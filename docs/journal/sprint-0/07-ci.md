# 7. GitHub Actions CI

**Sprint 0** · **Date:** 2026-10-14 · **Plan item:** GitHub Actions: lint + type check + tests on PRs and on `main` (Postgres as a service container)

## What and why
A workflow that runs on every PR and push to `main`: one job runs `make lint` and `make test` against a real Postgres service container, a parallel job builds the Docker image. Every change is checked in a clean environment built from the lockfile before it can merge.

| 2026-10-14 | Read-only `GITHUB_TOKEN`, 15-min job timeouts, cancel outdated runs | Least privilege; a hung test can't burn hours of minutes | Defaults (write token, 6h timeout) | — |

## Concepts

### GitHub Actions anatomy
A *workflow* (`.github/workflows/*.yml`) runs on *events* (`on: pull_request`, `push`). It has *jobs*, each on a fresh VM (*runner*), running in parallel unless linked by `needs:`. A job has *steps*: `uses:` runs a published action, `run:` runs shell commands. `services:` starts containers (our Postgres) before the steps; the steps run on the runner itself, so they reach a service at `localhost:<mapped port>` (in Compose it was the service name `db`). All `uses:` actions are downloaded before the first step, so a bad action reference fails the job in ~1s with no steps run.

### Action versions are maintainer conventions
`actions/checkout@v7` works because its maintainers move a `v7` tag along with each release; `astral-sh/setup-uv` publishes exact tags only (`v10.3.0`), so `@v10` doesn't exist. Exact versions (or commit SHAs) are the safer habit anyway: a moving tag can change between two runs.

### Reading a failed run from the terminal
`gh pr checks <n> --watch` waits for the result; `gh run view <run-id> --log-failed` shows only the failed steps; read the **last** `##[error]` line, everything above is runner setup.

### What pre-commit can't catch
Hooks check *the commit*, not the repo. They're skipped with `--no-verify`, they don't run on machines where `pre-commit install` wasn't run, and once a broken file is committed, a later commit that doesn't stage it passes the hooks. CI checks the whole repo on every push, in a clean environment built from `uv.lock`.

### CI caching
setup-uv stores downloaded packages under a key that includes a hash of `uv.lock`, so a dependency change gets a fresh cache and nothing else does. The cache is saved only after a **successful** job, so the first green run after a key change saves it and the next run restores it.

## Gotchas
!!! bug "CI job fails in 1s with no steps: `Unable to resolve action astral-sh/setup-uv@v10, unable to find version v10`"
    **Cause:** that repo publishes exact tags only; I assumed it had a moving major tag like `actions/checkout`.
    **Fix:** `setup-uv@v10.3.0`.
    **Lesson:** check an action's tags (`gh api repos/<owner>/<repo>/git/matching-refs/tags/v10`) before pinning.

!!! bug "CI cache key ends in `no-dependency-glob`"
    **Cause:** setup-uv resolves `cache-dependency-glob` relative to `working-directory`: `backend/uv.lock` became `backend/backend/uv.lock`.
    **Fix:** `cache-dependency-glob: uv.lock`.
    **Lesson:** third tool with the same relative-path trap (`.env`, `alembic.ini`, now this).

!!! bug "A commit passes pre-commit while the repo has a lint error"
    **Cause:** Python hooks only trigger when a `.py` file is staged; the broken file was committed earlier with `--no-verify`.
    **Fix:** CI caught it; fixed in a new commit.
    **Lesson:** hooks check the commit, CI checks the repo.

??? question "In Compose the API reaches Postgres at host `db`. In the CI job it uses `localhost`. Why the difference?"
    In Compose both run in containers on a shared network, where the service name is the hostname. In CI the steps run directly on the runner VM, and the service container's port is mapped to the runner, so it's `localhost:<mapped port>`.

??? question "Why does a typo in a `uses:` line fail the job in about a second, before any step runs?"
    The runner downloads every action the job uses before running the first step. If one can't be resolved, the job stops right there.

??? question "Why give the workflow a read-only `GITHUB_TOKEN` and a 15-minute timeout?"
    Least privilege: the checks only need to read the code, so a compromised step or action can't push or change the repo. The timeout stops a hung test from burning hours of the free minutes (the default is 6 hours).

## Explain it in 2 minutes
Every PR and every push to `main` runs a GitHub Actions workflow with two parallel jobs. The first starts Postgres as a service container and runs `make lint` and `make test`, the same targets I run locally, so the definition of "passing" lives in one place. The second builds the Docker image, so a broken Dockerfile shows up on the PR too. The workflow follows least privilege with a read-only token, has timeouts and cancels outdated runs, pins its actions to exact versions, and caches uv downloads keyed on the lockfile. Pre-commit is the fast first line, but it only sees what you commit and can be skipped, so CI is the real gate: it checks the whole repo in a clean environment.
