# 2. Clients and conversation tables

**Sprint 2** · **Date:** 2026-10-24 · **Plan item:** DB tables: clients, watchlists, conversations, messages, tool_calls

## What and why
A `clients` table and client ownership of the watchlist (now `watchlists`), plus `conversations`, `messages` and `tool_calls`. Market Desk is multi-client, and the Claude API is stateless: to continue a chat the whole history is sent again, so it has to be stored. `tool_calls` records what the agent actually ran and will hold write tools waiting for approval (task 4).

## Decisions
| Date | Decision | Why | Alternatives considered | ADR |
|---|---|---|---|---|
| 2026-10-24 | Tenancy through a `client_id` column, filtered in every query; the client comes from the request, never from the model | One schema, simple migrations; a tool argument for the client would let a confused or prompt-injected model touch another client's data | Schema or database per client (heavy for two clients) | [ADR-0007](../../adr/0007-clients-and-conversation-data-model.md) |
| 2026-10-24 | `client_id` on the existing watchlist table, unique per `(client_id, ticker)`, table renamed `watchlists` | One watchlist per client is all the product needs; plural matches the other table names | A separate `watchlists` + entries table for named lists | [ADR-0007](../../adr/0007-clients-and-conversation-data-model.md) |
| 2026-10-24 | `messages.content` is JSONB with the API's content blocks | The conversation can be replayed to the model unchanged; tool_result blocks keep their tool_use_id | Plain text (loses tool blocks); one table per block type | [ADR-0007](../../adr/0007-clients-and-conversation-data-model.md) |
| 2026-10-24 | `tool_calls` duplicates the tool_use block on purpose | "What the model saw" vs "what we ran"; failures and pending approvals become a `WHERE` | Only the JSON in `messages` | [ADR-0007](../../adr/0007-clients-and-conversation-data-model.md) |
| 2026-10-24 | UUID for `conversations.id`, integers for messages and tool calls | The conversation id appears in our API and URLs; the others are only reached through it, and integers give message order | Integers everywhere (guessable); UUIDs everywhere (no benefit) | [ADR-0007](../../adr/0007-clients-and-conversation-data-model.md) |
| 2026-10-24 | `role` and `status` as `String` + CHECK constraint | The database rejects bad values; adding one is a one-line migration | Postgres `ENUM` (needs `ALTER TYPE`); no constraint (bad values slip in) | — |

## Concepts

### Multi-tenancy with a client_id column
One database serves every client; each client-owned row carries `client_id`, and every query filters by it. Here `watchlist._entry(client_id, ticker)` builds the lookup so the filter can't be forgotten. The client must come from something the caller can't forge (the request's API key, task 5), carried to the tools in `ToolContext.client_id`, and never from the model's tool arguments: a model can be confused or prompt-injected into asking for another client's data.

### Expand, backfill, contract
How to add a `NOT NULL` column to a table that already has rows. **Expand:** add it as nullable (adding it as `NOT NULL` fails: `column "client_id" contains null values`). **Backfill:** `UPDATE` every row with a value (here, the `default` client). **Contract:** set `NOT NULL`, add the foreign key, swap constraints. A `server_default` would also work but stays behind afterwards, so a future insert that forgets the client would silently land in `default`. The same pattern scales to zero-downtime deploys, where the steps ship as separate releases.

### Renaming a table in Postgres
`ALTER TABLE ... RENAME` renames only the table. Its primary key, indexes and id sequence keep their old names (`pk_watchlist`, `ix_watchlist_cik`, `watchlist_id_seq`). They keep working (the column default points at the sequence by its internal id, not its name), but they no longer match the naming convention, and later autogenerated migrations look for names that don't exist. So the migration renames them too. Autogenerate can't do any of this: it sees a renamed table as one dropped and one created, which would lose the rows.

### Transactional DDL
In Postgres, `CREATE`, `ALTER` and `DROP` run inside transactions like data changes. Alembic wraps each migration in one ("Will assume transactional DDL" in the log), so a migration that fails halfway, for example on a `NOT NULL` that existing rows violate, rolls back entirely. MySQL can't do this: a failed migration there can leave the schema half-changed.

### ON DELETE CASCADE and RESTRICT
Foreign keys decide what happens to child rows when the parent is deleted. `CASCADE`: the children go too (deleting a conversation deletes its messages and their tool calls). `RESTRICT`: the delete is refused while children exist (a client with a watchlist can't be deleted by accident). This runs in Postgres, not in SQLAlchemy: we define no ORM relationships, so SQLAlchemy sends one `DELETE` and the database removes the rest.

### CHECK constraints
A rule the database checks on every insert and update: `CHECK (role IN ('user', 'assistant'))`. A bad value fails with `IntegrityError` naming the constraint (`ck_messages_role`), whichever code path wrote it. Python's `Literal` is only for the type checker and doesn't reach the database. Compared with a Postgres `ENUM`: same protection, but changing the allowed values is a one-line migration instead of `ALTER TYPE`.

### JSONB
Postgres's binary JSON type: stores any JSON structure, gives it back as Python lists and dicts, and can be indexed and queried (`content @> '[{"type": "tool_use"}]'`). Here it holds the API's content blocks exactly as sent and received. In the model, `Mapped[...]` gets the Python type (`list[dict[str, Any]]`) and `mapped_column(...)` the SQL type (`JSONB`): the two layers are separate.

### UUID vs sequential ids
A sequential id leaks information (how many rows exist) and invites guessing: if `/conversations/42` is yours, try 41. A random UUID (version 4, `uuid4()`) has nothing to guess. Use it for ids that appear outside the system (URLs, APIs); keep integers for rows only reached through a parent: smaller, faster to index, and ordered. A UUID isn't access control: the `client_id` filter is.

### Indexes on foreign keys
Postgres indexes primary keys and unique constraints automatically, but **not** foreign-key columns. Index the ones you query by: `messages.conversation_id` (read on every chat turn), `tool_calls.message_id`, `conversations.client_id`. A unique constraint whose first column is the foreign key already serves as its index (`(client_id, ticker)` on `watchlists`).

### Type inference in mapped_column
SQLAlchemy reads the SQL type from the annotation: `Mapped[int]` → `Integer`, `Mapped[str]` → `String` with no length, `Mapped[uuid.UUID]` → `Uuid`, `Mapped[datetime]` → `DateTime` without time zone, and `int | None` → nullable. Pass a type only when that isn't enough: `String(64)`, `Text`, `JSONB` (a dict or list can't be inferred), `DateTime(timezone=True)`, `BigInteger`.

## Gotchas
!!! bug "(exercise) The models module couldn't be imported: `role: Mapped[Literal] = [\"user\" | \"assistant\"]`"
    **Cause:** the line assigns a list to `role` (no column), and `"user" | "assistant"` raises `TypeError` at import: `|` doesn't work between strings. `Literal` is a type-checker concept, not a SQL type; the same for `status`.
    **Fix:** `role: Mapped[str] = mapped_column(String(20))` plus `CheckConstraint("role IN ('user', 'assistant')", name="role")` in `__table_args__`.
    **Lesson:** `Mapped[...]` is the Python type, `mapped_column(...)` the SQL type; database rules go in constraints.

!!! bug "(exercise) `Mapped[JSONB]` and `Mapped[int]` with `nullable=True`"
    **Cause:** `JSONB` is a SQL type, not a Python type; and `Mapped[int]` says "never null" while `nullable=True` says the opposite.
    **Fix:** `Mapped[list[dict[str, Any]]] = mapped_column(JSONB)`; `Mapped[int | None]` without `nullable`.
    **Lesson:** let the annotation carry the Python type and nullability; mypy then enforces the `None` check in code.

!!! bug "mypy: `Incompatible return value type (got \"Select[WatchlistEntry]\", expected \"Select[tuple[WatchlistEntry]]\")`"
    **Cause:** in SQLAlchemy 2.1, `select(Model)` is typed `Select[Model]`; the `Select[tuple[...]]` form is from 2.0.
    **Fix:** annotate `-> Select[WatchlistEntry]`.
    **Lesson:** typing details change between minor versions; trust mypy's message over memory.

## Check questions
??? question "Why couldn't the migration add `client_id` as `NOT NULL` in one step?"
    The table already had a row (AAPL), and a new column without a default is NULL for existing rows, so Postgres refuses: `column "client_id" contains null values`. With transactional DDL the whole migration rolls back. A `server_default` would avoid it but stay behind, sending future inserts that forget the client to `default` silently; nullable → backfill → `NOT NULL` leaves nothing behind.

??? question "Clients A and B both watch AAPL; A removes it. Does B still get alerts? Which table decides?"
    Yes, and alerts are global anyway (one Slack message per filing). `watchlists` decides whether a company is checked at all: `check_new_filings` starts with `SELECT DISTINCT cik FROM watchlists`, and B's row keeps Apple's CIK in it. `seen_filings` decides something else: whether a given filing was already announced (the outbox).

## Explain it in 2 minutes
Market Desk serves several clients from one database, so every client-owned row has a `client_id` and every query filters by it; the client comes from the request, never from the model, so a model can't reach another client's data. Moving the existing watchlist under clients took an expand-backfill-contract migration: add the column nullable, give existing rows the default client, then make it required. For the agent, the Claude API is stateless, so conversations, messages and tool calls are stored: messages keep the API's raw content blocks in JSONB so a conversation can be replayed exactly, and tool calls are duplicated into their own table because what the model saw and what we ran are different questions, and that table will also hold write tools waiting for approval. Conversation ids are UUIDs because they appear in URLs; the database enforces the rest with foreign keys that cascade or restrict, and CHECK constraints on roles and statuses.
